01 / 05 배경과 목적 · 왜 만들었나

복잡한 네트워크 설정, 장애 시 처음부터 다시 만들 수 있는가?

서버·DB 데이터 백업만으로는 수십 개 규칙과 참조가 얽힌 제어 평면(Control Plane) 형상을 되살릴 수 없다.

armbackup

현장의 공백 (Pain Point)

해결 대상 문제

기존 백업의 사각지대

Azure Backup은 VM 디스크·DB 데이터 중심이라 네트워크·WAF 설정 이력을 보관하지 않음

높은 수작업 재구성 비용

Application Gateway·Load Balancer 오변경 시 라우팅·프로브·풀을 수동 복구하는 데 장시간 소요

단순 템플릿 내보내기의 실패

ARM 원본 JSON에는 읽기 전용 값·외부 참조가 섞여 있어 그대로 재전송하면 거부됨

해결 목표

armbackup이 해결하는 것

핵심 목적 3가지

일일 형상 자동 보존과 변경 추적

매일 제어 평면 원본 설정을 사설 저장소에 기록하고 날짜별 변경 이력을 시각화

시점 비교(Diff) 기반 안전 복원

백업 시점과 현재 설정의 차이만 정확히 대조한 뒤 검증된 절차로 원복·재생성

운영 무간섭 독립 복제(Clone)

원본 리소스를 건드리지 않고 동일·타 리소스 그룹 및 구독에 검증용 복제본 생성

핵심 목적 빈 리소스 생성이 아니라, 다시 세팅하기 까다로운 운영 네트워크 형상과 연결을 안전하게 재현한다.

02 / 05 제품 컨셉 · 무엇을 다루고 무엇을 덜어냈는가

서버 이미지 백업이 아닌 "검증된 형상 기록 + 의미 인식 재현기"

모든 리소스를 얕게 복제하는 범용 도구 대신, 재구성 비용이 큰 핵심 네트워크 묶음을 끝까지 책임진다.

Concept
비대상 · 데이터 평면 (Data Plane)
VM OS·디스크 · DB 내부 데이터 · 실시간 트래픽 · 비밀 원문
집중 범위 · 제어 평면 형상 (Control Plane)
라우팅·리스너·프로브·WAF 정책·백엔드 풀 및 연관 리소스 참조
대상 선정

고비용 복합 리소스 집중

주 리소스 선택 시 복구에 필요한 동반 리소스를 같은 스냅샷 단위로 자동 동시 수집

수집·보관

탐색과 상세 수집 분리

비동기 색인(ARG)에 의존하지 않고 실제 Provider API 응답과 무결성 해시를 불변 보관

운영 콘솔

단일 웹 워크플로 연결

명령줄 스크립트에 머물지 않고 운영자가 변경 시점을 찾아 비교·승인하는 웹 콘솔 제공

핵심 컨셉 탐색(ARG) · 수집(REST) · 검증(SHA-256) · 재현(웹 콘솔)을 하나의 App Service 환경에 통합했다.

03 / 05 설계 고민 · 엔터프라이즈 제약을 어떻게 풀었는가

실제 고객 환경의 3가지 현실 제약과 아키텍처 선택

폐쇄망 보안 정책, 무(無) 데이터베이스 원칙, 운영 신뢰성 기준이 모든 설계 결정을 이끌었다.

Trade-offs
Q1

폐쇄망 사설 저장소 접근

공용망 차단 Storage PE + 압축 배포 제약

초기 검토안의 한계

기본 Cloud Runbook은 사설 PE 직접 접근이 어렵고, Oryx 압축 배포에서는 하위 WebJob 파일이 노출되지 않음

App Service VNet 통합 + 내장 수집기

VNet Integration으로 사설 Blob에 직접 연결하고, 웹 프로세스 내부 스케줄러가 백그라운드 수집 수행

Q2

데이터베이스 사용 불가

별도 DB 없이 다수 백업·변경 달력 고속 조회

실시간 직접 조회의 한계

화면 진입마다 수십 개 백업 Blob과 실시간 ARM API를 직접 읽으면 응답 지연과 API 호출 한도 발생

불변 Blob 원본 + 스냅샷 뷰 캐시

5분 주기 및 작업 직후 화면용 집계 스냅샷을 Blob에 게시해 DB 없이도 즉시 로딩과 읽기 전용 폴백 보장

Q3

완료의 정직한 경계

부분 누락 방지와 외부 로그 장애 격리

단순 응답 저장의 착시

일부 동반 리소스가 누락된 채 완료 처리하거나, 반대로 로그 설정 오류 때문에 핵심 백업 자체가 멈출 위험

COMPLETE 표식 엄격화 + 로그 Fail-Open

동반 리소스와 해시 검증 통과 시에만 완료 표식을 발행하되, Log Analytics 오류는 경고로 분리해 업무 지속

설계 원칙 인프라를 새로 늘리지 않고(No-DB · 단일 Plan 공유), 무결성과 가용성을 동시에 확보했다.

04 / 05 구현 난제 · 왜 복원과 복제가 가장 어려운가

백업한 원본 JSON을 그대로 PUT하면 왜 실패하는가?

Load Balancer와 Application Gateway에는 4가지 Azure 제어 평면 제약이 동시에 얽혀 있다.

Hard Parts
01

연관·종속 리소스 수명주기 불일치

순서 · 덮어쓰기

1:1 배타(PIP)·공유(WAF)·하위 귀속(Pool)의 생성 순서가 다르며, 배열 전체 PUT 시 사용 중 풀이 삭제될 위험 존재

02

복제 시 고유 식별자·주소 충돌

Unique 제약

특히 Application Gateway v2는 동적 사설 IP를 지원하지 않아 동일 서브넷 복제 시 새 정적 IP 재할당이 필수

03

Backend Pool의 NIC 중복 등록 불가

역참조 · 중복 차단

풀의 NIC 목록은 읽기 전용 역참조이며, 운영 중인 NIC를 원본에서 떼지 않고 복제 풀에 중복 연결할 수 없음

04

생성 후 불변 속성 및 상태 전이 함정

불변 · 런타임

불변 속성이 다르면 업데이트가 거부되며, 중지된 게이트웨이는 PUT 수신 즉시 과금·트래픽이 재개됨

핵심 난제 복원·복제는 단순 파일 복사가 아니라 리소스 간 관계·식별자·상태를 재해석하는 컴파일 과정에 가깝다.

05 / 05 해결 아키텍처 · 어떻게 안전하게 풀어냈는가

선언형 의미 규칙과 4단계 안전 파이프라인으로 해결

운영자가 내부 JSON 경로나 제약 조건을 외우지 않아도 실행 전에 충돌을 자동 보정·검증한다.

Solution
STEP 01

선언형 명세 판별

리소스별 6종 관계 분류와 불변·상태 규칙(M0~M4)을 자동 대조

STEP 02

사전 충돌 자동 보정

1:1 PIP 자동 동반 · 새 정적 IP/DNS 추천 · LB 임시 IP 풀 우회

STEP 03

안전 백업 & 승인

변경 직전 현재 형상을 먼저 안전 백업하고 계획 해시(SHA-256) 검증

STEP 04

순서 적용 & 재검증

선행 → 부모 → 하위 순서로 PUT 적용 후 실제 반영 형상을 재비교

실수 방지(Poka-yoke) UI

자동 처리 항목은 숨기고 꼭 필요한 선택만 모달·추천값으로 제시

확장 가능한 레지스트리

유형별 분기 코드 대신 선언형 명세로 차기 VM·VMSS까지 확장 대비

투명한 감사와 안전성

제외·보정 사유와 부분 실패까지 숨김없이 기록해 운영 신뢰 확보

결론 복잡한 Azure 네트워크 설정을 누구나 안심하고 보관·비교·복원·복제할 수 있는 실용적 통제 기반을 완성했다.
