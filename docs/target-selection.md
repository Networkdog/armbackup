# 백업·복원 대상 선정 — 복잡한 설정의 재구성 비용 중심

> 범위: 고객의 복잡한 형상 중심 대상 선정 기준과 격리 LAB의 후속 구현. 일반 CLI 기본 수집 정책·운영 지원 범위를 자동 확대한 기록이 아니다.

**한 줄 요약** — 자원을 쉽게 만드는지가 아니라, 필요한 설정과 연결을 다시 구성하는 데 드는 시간·위험을 기준으로 백업·복원을 우선한다.

## 고객 요구와 실체

사용자의 설명은 다음과 같다.

> 기본적으로 KT Cloud 고객이 백업과 복원을 원하는 리소스 종류는 주로 세팅하기 어렵고 복잡하여 시간이 많이 걸리거나, 단순히 생성 하는 것만으로는 해결이 되지 않는 것들이다. 가령, Application Gateway + WAF, Load Balancer, Front Door, Route Table, Network Security Group 등이다. 생성 후 간단한 설정만으로 끝나는 리소스들은 굳이 백업이나 복원이 필요하지 않을 수 있다.

따라서 이 과제의 중심은 **모든 종류의 리소스를 동일하게 백업하는 것**이 아니라, **복잡한 설정·정책·연결을 재현하는 수작업을 줄이는 것**이다. ≈ 빈 서버를 배포하는 자동화보다 서비스 설정·운영 정책을 재적용하는 구성 관리에 가깝다. 업무 데이터 평면을 제외한다는 기존 요구는 유지한다. (근거: 위 사용자 설명과 [기존 과제 범위](handoff.md))

“간단한 리소스는 필요하지 않을 수 있다”는 말은 일괄 제외 승인이나 특정 유형의 영구 제외를 뜻하지 않는다. 고객별 중요도·실제 설정·의존 관계를 확인해 선정한다.

## 우선 후보와 현재 지원을 구분

아래는 **고객이 제시한 우선 후보**다. 유형별 전용 수집·Diff·복원 프로필이 모두 구현됐다는 뜻은 아니다.

| 우선 후보 | 후속 설계에서 정할 복구 단위 | 현재 범위와 구분 |
| --- | --- | --- |
| **Application Gateway + WAF** | Gateway 설정·정책과 연결을 함께 검토하는 조합 | HTTP WAF_v2 LAB 프로필; 인증서·업무 백엔드 복구 제외 |
| **Load Balancer** | 부하분산 설정과 적용/참조 관계 | Standard LB + 독립 Pool 프로필; VM/NIC 업무 데이터 복구 제외 |
| **Front Door** | 대상 배포 형태의 설정·정책·참조 관계 | Standard와 포함 child 프로필; 미검토 SKU/Private Link/운영 WAF 별도 |
| **Route Table** | 경로 설정과 실제 적용 범위 | 격리 LAB 형상 복원과 운영 연결 복구는 구분 |
| **Network Security Group** | 보안 규칙과 실제 적용 범위 | 격리 LAB 형상 복원과 운영 연결 복구는 구분 |

현재 LAB은 포함/연관/공유·주소 경계와 전용 투영·의존 순서를 구현했다. 모든 구성·운영 리전/SKU·인증서·비밀·권한·업무 데이터의 일반 복구까지 지원한다는 뜻은 아니다. 정확한 [복원 계약](restore.md)과 [실제 검증](validation.md)을 따른다.

## 선정 기준안

리소스 유형은 우선순위의 출발점이고, 실제 인스턴스의 다음 조건을 함께 평가한다.

1. **재구성 노력:** 생성 후 설정할 항목이 많거나 규칙/정책을 다시 입력하는 시간이 큼.
2. **관계의 복잡성:** 단일 자원을 생성하는 것만으로 끝나지 않고 다른 자원·정책·참조·적용 관계가 필요함.
3. **운영 위험:** 잘못된 설정 재적용이나 현재 정상 변경의 덮어쓰기가 서비스/보안에 영향을 줄 수 있음.
4. **변경·감사 가치:** 설정 변경을 추적·비교하거나 검토한 시점으로 되돌릴 필요가 있음.
5. **검증 가능성:** 필수 형상을 수집하고, 안전한 계획·승인·적용·사후 검증까지 정의할 수 있음.

위 기준은 설계 제안이다. 유형별 점수·고정 임계값·복구 시간은 아직 정하지 않는다. 동일 유형이라도 설정이 단순하거나 다른 승인된 자동화로 재현할 수 있으면 우선도가 달라질 수 있다.

## 전체 Discovery와 선택적 백업은 다른 범위

**ARG 전체 Discovery는 유지**해 자원 목록·관계를 파악한다. 그중 무엇을 상세 백업·비교·복원 지원할지는 별도 대상으로 선정하는 방향을 권고한다.

| 역할 | 목적 | 처리 방향안 |
| --- | --- | --- |
| **주요 형상 대상** | 재구성 비용이 큰 설정을 보존·재현 | 유형별 필수 형상·Diff·복원 프로필과 인수 기준 정의 |
| **의존·참조 대상** | 주요 대상의 정상 복구에 필요한 관계 유지 | 기존 자원 재사용인지 재생성인지에 따라 참조·필요 설정·재연결 정보를 보관 |
| **인벤토리만/승인 제외** | 상세 백업 가치가 낮거나 별도 수단으로 재현 | Discovery에서는 보이되 비대상·사유를 표시하고 상세 수집/복원과 구분 |

이 역할 분리는 후속 정책 모델 제안이며 현재 설정에 새 JSON 키를 추가한 것은 아니다. 현재 [대상 정책 UI](comparison-ui.md)와 [수집 설정](configuration.md)의 스코프·유형·태그·제외 기능에 어떻게 반영할지 별도 검토한다.

**단순해 보여도 의존성이면 누락하지 않는다.** 주요 자원을 복원할 때 필요한 대상은 기존 자원과의 연결 확인, 재생성 필요 여부, 식별자·권한 주체·인증서/비밀 참조의 재연결 계약 등을 검토한다. 비밀값·업무 데이터를 무조건 백업하라는 뜻이 아니며, 필요 입력·참조·별도 승인 범위를 명시한다.

“백업 비대상”·“승인 제외”·“필수 형상 미수집/실패”는 서로 다르다. 필수 의존 설정을 읽지 못한 상태를 완료로 바꾸거나, UI에서 비교하지 않은 자원을 Green 동일로 표시하지 않는다.

## 복원·UI에 반영할 후속 방향

- **Create-only:** 빈 자원이 생성됐다는 사실만으로 완료하지 않고, 주요 설정과 필요한 적용/연결을 재현한 범위를 검증한다.
- **Update-only:** 해당 유형의 설정 차이·복원할 범위·정상 변경 보존·규칙 삭제·연결 변경을 계획에 드러낸다.
- **UI 대상 설정:** 우선 유형 프리셋과 주요/의존/인벤토리 역할, 선정·제외 사유, 현재 지원 프로필과 검증 상태를 구분해 보여주는 안을 검토한다.
- **TreeGrid Diff:** 비교 가능한 형상 범위와 의존 관계를 표시하고, 단순 인벤토리·비대상·미지원·미확인을 실제 형상 동일/변경과 섞지 않는다.
- **완료와 보고서:** “생성/쓰기 성공”과 “필수 형상 재현/기능·연결 검증”을 분리하고, 실제 확인한 범위를 기록한다.

이는 새 구현 요구를 구체화하는 방향이지 기존 LAB의 보호 경계를 완화하는 승인이 아니다. 현재 단일 소유 RG·검토한 유형·안전 백업·승인·사후 비교의 제한을 유지한다.

## 다음 결정·검증

1. 고객이 가장 많은 시간을 쓰는 실제 설정 예시와 복구 시나리오를 유형별로 확보한다.
2. 첫 운영 후보와 복구 단위·필수 형상·참조/재생성 범위를 선정한다. 위 다섯 유형 내부의 정확한 구현 순서는 아직 미확정이다.
3. API 수집 범위·누락 설정·지원 버전·정규화·복원 프로필을 정의한다.
4. 격리 환경에서 Create/Update·연결 재현·미수집·부분 실패·현재 변경 충돌을 시험한다.
5. 기존 수집·UI 정책에 대상 선정안을 적용할 때 명시적으로 변경하고, 단순 리소스를 일괄 제외하기 전에 의존성을 대조한다.

이번 기록은 **고객의 대상 선정 목적·우선 후보를 반영한 문서 변경**이다. 새 유형의 상세 API를 재조사하거나 코드·설정·Azure 자원을 변경하지 않았다. 현재 검증 결과는 [validation.md](validation.md)를 따른다.
