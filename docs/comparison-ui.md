# 웹 인터페이스 설계 — 대상 설정·백업 현황·복원·로그

> 범위: 승인된 테스트 구독 전체의 화면·데이터·안전 설계, 예시 프리뷰와 로컬/인증된 App Service 콘솔. **다중 사용자/테넌트 운영·범용 복구는 제공하지 않는다.**

**한 줄 요약** — 네 화면과 MSP 업무 프리셋을 제공하고, 명시적인 LAB 모드에서는 실제 ARM·Activity Log·Log Analytics와 검증된 안전 백업·형상 복원을 연결한다.

## 핵심 요약 (3분)

- **사용자 요구:** 백업 대상 설정, 백업 현황, 복원, 로그 열람의 네 화면을 제공한다. 대상 설정은 Management Group·Subscription·Resource Group·Resource, 리소스 종류와 태그를 다룬다.
- **최신 행 표시:** 변경 위험도가 아니라 최근 일반 백업 상태를 사용한다. 성공 초록, 실패/없음/24시간 경과 빨강, 미확인/제외 회색이다. 행의 10일 달력은 변경 기록 수를 파랑으로 표시하며 백업 시각은 상대시각으로 표시한다. 아래의 초기 위험도 분류 제안은 현재 행 음영 정책이 아니다.
- **호스팅 확정:** 비교/복원 UI는 **App Service**를 사용하고 백업 실행기와 **동일 App Service Plan**을 이용한다. 같은 Plan의 별도 Web App·관리 ID 분리는 권장안이다.
- **기본 화면안:** 백업 시점 선택 → 비교 범위/현재 조회 → TreeGrid → 자원별 속성 차이 상세. 계층과 상세 비교를 한 흐름으로 연결한다.
- **양측 합집합:** 같은 Resource ID로 대응하며, 최종 TreeGrid 행은 선택한 백업의 자원이다. 현재에만 있는 자원은 별도 안내·목록으로 제공하고 자동 삭제·복원하지 않는다.
- **정확한 상태:** 동일·변경·백업에만·현재에만과 **비교 대기/미확인**을 구분한다. 조회 오류를 자원 삭제나 형상 동일로 표시하지 않는다.
- **관측 시각·커버리지:** 백업 시각, 현재 조회 시각, API/정규화 차이와 제외 설정을 보여준다. “현재”나 “동일”의 의미를 과장하지 않는다.
- **현재 구현:** 설정한 구독 전체 RG의 실환경 콘솔에서 **복원 복제의 날짜별 백업 달력**을 제공한다. 별도 변경 달력 메뉴와 별도 `자원·관계 작업대` 메뉴는 없다(관계·묶음 검토는 복원 복제 화면 안에서 한다). 검토한 NSG/RT·HTTP Gateway/WAF·Standard LB/독립 Pool·Front Door Standard 설정의 단일/묶음 계획을 제공한다. [복원 프로필과 제약](restore.md)을 확인한다.
- **복원·복제 화면 구성:** 메뉴로 먼저 들어오든 백업 현황에서 항목을 골라 들어오든 화면이 같다. 맨 위에 선택한(또는 선택할) 백업 항목 정보를 두고, 그 아래에 해당 항목만의 백업 달력을 둔다. 메뉴로 먼저 들어오면 백업이 있는 항목 목록에서 고르고, 백업 현황에서 들어오면 그 항목을 미리 선택해 줄 뿐이다. `항목 변경`으로 언제든 다른 항목을 고를 수 있다.
- **변경 달력(백업 현황 표, 최근 10일):** 한 칸이 모양·색·기호로 백업과 변경을 함께 보여 준다. ✓ 녹색=백업됨·변경 없음, Δ 파랑(진할수록 변경 많음)=형상 변경, + 청록=백업 목록 추가, × 빨강=다음 백업 목록에서 제외 또는 현재 부재 확인(삭제됨), ○ 원=첫 백업, ? 점선=비교 미확인, 빈 칸=백업 없음. “목록 제외”는 삭제 확인이 아니며, 현재 리소스의 부재를 ARM으로 확인한 경우에만 오늘 칸을 삭제됨으로 표시한다.
- **관리자 메뉴:** 일일 백업 시각(KST, 하루 1회·사용 여부) 저장과 Storage 백업 전체 삭제를 제공한다. 삭제는 구독/RG 값과 문구를 모두 입력해야 하며 `runs/`·화면 캐시·복원 계획만 지운다. 정책·예약 설정·작업 이력은 유지한다.

사용자 요구 외의 세부 정책은 **설계 제안**이다. Python 서버와 외부 의존성 없는 HTML/CSS/JavaScript를 사용한다. 기본 모드는 loopback이고 `--hosted`는 App Service EasyAuth를 필수로 요구한다. 프로덕션 다중 사용자 지원 계약은 아니다. [배포 경계](deployment.md), [복원 상태](restore.md)를 따른다.

## 최신 대상 선정 요구 — 복잡한 형상 중심

KT Cloud 고객은 **설정이 복잡하고 재구성 시간이 큰 자원**에 백업·복원 가치를 둔다. 우선 후보는 Application Gateway + WAF, Load Balancer, Front Door, Route Table, NSG다. 간단한 자원은 상세 백업이 필수가 아닐 수 있지만 주요 대상의 의존/참조 역할을 확인한다. [선정 기준·현재 지원 범위](target-selection.md)를 따른다.

관계 작업대는 **직접 선택·포함·연관·공유·IP/FQDN 주소 참조**를 구분한다. 공유/주소 대상은 자동 복구하지 않으며, 인벤토리만인 자원이나 미확인을 Green으로 만들지 않는다. 사용자 승인으로 설정한 단일 테스트 구독의 모든 RG를 허용하며 다른 구독은 차단한다.

### 복원 복제의 관계 검토 (구 자원·관계 작업대)

별도 `자원·관계 작업대` 메뉴는 제거했다. 같은 검토 화면은 `복원 복제`에서 단일/묶음 복원이 필요할 때 열린다. 시작점은 **동일 run의 검증된 백업**이다. 단일/다중 선택 → 포함 자원 자동 포함 → 필요할 때 연관 추가 → 공유·주소 경계 확인 → 원래 ID 재생성/기존 업데이트 → 서버 확정 순서 → 전체 안전 백업 → 전체 적용 후 비교 순서다. 행별 최신 뷰를 하나의 동시점 묶음으로 취급하지 않는다.

- Front Door의 endpoint/origin group/origin/route/rule set/rule과 LB의 독립 backend pool을 포함한다. 대상 정책에서 부모 종류·부모 범위를 선택해도 해당 포함 자원을 수집한다.
- **독립 설정 복제**는 구독 안에서 이름 접두사·원본→대상 표·ARM 참조·PIP DNS 매핑을 서버 계획으로 검토한다. 기본은 각 원본이 있던 RG 안에 새 ID를 만들며, 대상 구독·리소스 그룹을 고르면 그 RG에 만든다([복제 위치](restore.md#복제-위치-다른-구독리소스-그룹)). 이미 있는 대상은 덮어쓰지 않는다. 공유 Subnet/백엔드 주소는 별도다.
- Gateway의 맥박 아이콘은 **현재 ARM backendhealth**와 **최근 24시간 지정 Workspace의 WAF/접속 로그**를 연다. 수신 0건·조회 실패·실제 health 결과를 구분한다.
- 가변 폭 작업 목록/관계 검사기를 사용하고 화면 최대 폭 제한을 없앴다. 색·픽토그램·짧은 상태·단계 순서를 중심으로 표현하고 큰 표는 자체 스크롤한다.
- 계획/승인 후 선택·방식·티켓·사유·경계를 바꾸면 기존 계획을 무효화한다. 화면 이동 뒤 늦은 응답은 폐기하며 실패한 실행은 재승인해야 한다.
- [전체 폭의 검증된 원본·관계 작업대](images/complex-workbench.png). 화면의 `abx-` 부재 행은 기능 검증 후 시험 자원을 정리한 결과이며, 원본·로그는 유지했다.

## MSP 업무 모델과 실환경 화면

백업 대상 설정은 **01 수집할 리소스 종류 → 02 허용된 리소스 체계 → 03 태그 조건** 순서로 진행한다. 예시 화면도 같은 순서를 사용하며 표시 순서만 바꾼다. 기존 정책의 선택값과 종류·범위·태그의 교집합 계산은 유지한다.

실환경 설정의 기본 버튼은 **대상 저장 후 백업**, 보조 버튼은 **저장만**이다. 통합 동작은 `POST /api/backup`에 `policy`를 포함해 서버 작업 한 건으로 제출한다. 서버가 정책을 검증·저장한 뒤 그 정책 그대로 백업하므로 다른 접속자가 저장 정책을 바꿔도 해당 작업의 대상을 바꾸지 않는다. 저장 실패 시 백업을 시작하지 않는다. 저장 후 백업이 실패하면 정책은 유지하고 **대상 저장 완료 · 백업 실패**와 작업 ID를 표시한다. `policySaved`·`savedPolicy`는 진행·완료 기록에도 남긴다. 저장만은 `POST /api/policy`로 기존처럼 동작하며, 현황 화면의 백업은 저장된 대상을 사용한다. 예약 CLI 설정은 두 동작 모두 변경하지 않는다. 실제 수집을 하지 않는 예시 프리뷰는 브라우저 설정 저장만 제공한다.

종류 선택은 인벤토리가 아닌 [공식 지원 카탈로그](../src/armbackup/ui_static/resource-support.json)의 Application Gateway·Load Balancer만 표시하며 인스턴스가 없어도 숨기지 않는다. 검증한 SKU/프로토콜은 각 선택지에 표시한다. WAF Policy·Public IP·독립 Backend Pool은 주 대상의 참조/포함 관계로 자동 수집하며 공유 VNet/Subnet은 별도다. 수집 중 참조가 바뀌어 관련 원본이 빠지면 완료 표식을 만들지 않는다. 기존 비공식 종류 정책은 명시적 전환 전까지 보존하되 새 일반 백업은 막고 다시 저장하도록 알린다. [지원 범위와 등록 기준](target-selection.md)을 따른다.

백업 현황은 **행 선택과 복원 진입**만 제공한다. 행을 고를 때 하단에 자동 형상/Diff 패널을 생성하지 않는다. 속성 비교는 복원 달력의 ‘원본 비교’와 복원 계획 검토에서 제공하며 선택·키보드 탐색·복원 가능 여부 검증은 유지한다.

### 최신 백업 상태·최근 10일 보기

기본 글꼴은 브라우저 100%에서 기존 125% 줌 수준을 유지한다. `rem`과 `em`으로 사용자 글꼴/줌 설정을 존중하되 16:9 화면을 위해 장식용 영문 머리말·제목 반복 설명을 제거하고 상단·패널·행의 세로 여백을 별도로 압축했다. 제목과 실행 버튼을 같은 줄에 배치하며 좁은 화면에서는 줄바꿈한다. 큰 표와 변경 달력은 자체 스크롤을 유지한다.

`inventory_scope=subscription`을 명시하면 현재 구독의 모든 RG에서 **기존 검토된 네트워크 종류**를 조회·백업한다. 관리 그룹 상위 체계는 ARG의 실제 구독 ancestry에서 읽는다. 설정의 체크박스 목록은 **관리 그룹·구독·RG까지만** 표시하고 개별 자원은 표시하지 않는다. 기존 개별 자원 정책은 그대로 보존하며 상위 범위의 부분 선택으로 표현한다. 상위 범위를 선택한 뒤 하위 RG 하나를 해제하면 나머지 형제 범위를 유지한다. 관리 그룹 선택은 서버에 설정한 구독으로만 투영하며 다른 구독으로 권한을 확대하지 않는다. 기존 LAB 정책은 전체 구독 정책으로 자동 변환하지 않는다.

현재 `inventory_scope=subscription`은 조회·백업·복원·복제 모두 설정한 단일 구독 전체 RG를 허용하며 기본값도 `subscription`이다. LAB 태그·특정 RG 이름은 요구하지 않는다. 기존 `lab` 값은 이전 설정/시험 도구의 명시적 호환 모드이며 현재 배포에는 사용하지 않는다. 복원 프로필·티켓·일회 계획·안전 백업은 유지하고, 구독 ID 최종 확인은 복원에만 적용한다(복제는 면제). 관리 그룹 조회 실패는 경고로 표시하고 가상 관리 그룹을 만들지 않는다. 범위를 바꾸면 캐시 identity가 달라지고 예전 계획의 scope 확인도 실패한다.

상시 LAB 배너·반복 설명 카드는 없애고 연결 범위·저장 원천·복구 제외 사항을 시작 안내 모달로 모은다. 같은 탭에서는 확인 뒤 다시 띄우지 않으며 조회/복원 범위·저장 원천·복원 활성화가 바뀌면 재안내한다. 상단 안내 아이콘으로 언제든 다시 열 수 있다. 확인 기록은 안내 중복 방지일 뿐 실행 승인이나 서버 인가가 아니다. 저장을 거부하는 브라우저에서는 명시적으로 알리고 다음 시작에 다시 안내한다. 쓰기 잠금·진행 상태·실행 직전 파괴적 변경 경고는 계속 해당 작업 위치에 표시한다.

전역 오류는 상단 배너 대신 별도의 네이티브 `alertdialog` 모달로 표시한다. 실환경·프리뷰·앱 모듈 로딩 실패에 같은 UI를 사용하며 오류 메시지 때문에 본문 레이아웃을 밀지 않는다. 기존 상세/안내 모달은 덮어쓰지 않으며 오류창을 닫으면 기존 작업으로 돌아간다. 확인·닫기·Escape를 지원하고 인증 오류에는 다시 로그인/새로고침, 일반 오류에는 상태 재확인을 제공한다. 백업·복원을 자동 재제출하지 않는다. 사용자가 닫은 동일한 백그라운드 오류는 반복해서 열지 않되 명시적 재시도 실패는 다시 알린다. 갱신 성공은 해당 조회 오류만 해제하며 다른 작업의 오류를 지우지 않는다. 리소스별 미확인·진단 경고 등 데이터 상태는 해당 화면에 유지한다.

공통 상단의 연결 정보 띠와 사이드바의 워크스페이스 카드는 표시하지 않는다. 워크스페이스·구독·조회/복원 범위·저장 원천·ARM 관측 시각·현재 조회 요약은 **백업 대상 설정 → 연결 정보**에서 필요할 때 펼쳐 본다. KST/UTC 선택도 설정으로 옮기며 선택한 시간대는 현황·변경 달력·관계 작업대·로그에 계속 적용한다.

실환경 현황의 행 음영은 변경 위험도가 아닌 **최신 일반 백업 상태**다. 마지막 해당 자원 백업의 실패(완료/무결성 미확인 포함), 검증된 백업 없음, 일일 기준 **24시간 이상 미백업**은 빨강이다. 성공은 초록, 범위 제외·관측 한도 때문에 판정할 수 없음은 회색이다. 안전 run·다른 자원의 실패·복원 작업 실패는 일반 백업 성공을 대체하지 않는다. 과거 비교 기준을 선택해도 상태는 최신 일반 백업 기준을 유지한다.

`변경 달력 · 최근 10일` 열은 KST/UTC의 오늘 포함 10개 날짜를 왼쪽→오른쪽으로 표시한다. 파랑 농도는 변경 기록 수이며 임의의 위험 분류가 아니다. 미관측/첫 관측/비교 미확인/검증된 무변경을 구분한다. 클릭하면 복원 메뉴의 해당 리소스·날짜 백업 탐색으로 이동한다. 복원 달력의 농도는 백업 자원 수이므로 이 미니 변경 열과 단위가 다르다. 백업 형상은 분/시간/일/주 상대시각이며 툴팁에 정확한 시각을 제공한다.

`리소스 그룹 보기`에서 체계별/종류별을 선택한다. 종류별도 동일한 원본 Resource ID·필터·개별 선택·키보드 펼침/접기를 유지하며 보기 변경이 복원 단위를 변경하지 않는다. 두 보기 모두 주 대상(Application Gateway·Load Balancer 등)만 최상위 행으로 보이고, 이름 계층으로 포함된 하위 리소스(Backend Pool)와 원본 응답이 ID로 참조하는 연관 리소스(Public IP·WAF Policy)는 그 아래 종속 행으로 접어 둔다(기본 접힘). 모체 행에 `하위 N개`를 표시하고, 접힌 하위 중 백업 문제가 있으면 개수를 빨강으로 알린다. `→`/`←` 키 또는 화살표 버튼으로 펼치고 접는다. 필터에 걸린 하위는 모체를 문맥으로 함께 보이며 펼친다. 여러 주 대상이 참조하는 연관 리소스는 ID 순으로 첫 주 대상 아래에 두고 `공유`로 표시한다. 종속 관계는 화면 표시용이며 복원 단위를 바꾸지 않는다. 검증된 일반 백업이 전혀 없는 현재 자원도 최신 보기에서 보여주되 복원용 snapshot을 만들어내지 않는다.

**계층 표시 방식(A+E).** 백업 현황의 계층 표는 azfirewallagent의 재사용 TreeGrid·TreePane을 그대로 옮겨(`tree-grid.mjs`, `tree-pane.mjs`) 두 배치를 한 화면에서 오간다. 계층 패널을 접고 펼치는 것이 곧 배치 선택이다. 기본은 펼침이다.

- **E 형(패널 펼침):** 왼쪽 `리소스 계층` 트리(Management Group › Subscription › Resource Group, 종류별 보기에서는 종류 목록)가 계층을 맡고, 표에는 선택한 범위의 자원만 평평하게 보인다. 트리 항목에는 자원 수와 백업 문제 수(빨강 배지)를 함께 보이며, 표 위의 범위 띠가 선택 경로를 반복하고 `전체`로 해제한다. 트리는 WAI-ARIA `tree` 키(↑↓·Home·End·←→·Enter)를 지원하고 너비를 끌거나 ←/→(Shift는 큰 단위)로 조절하며 더블클릭으로 되돌린다. 폭이 820px 미만이면 트리는 좁은 레일이 되어 표 위에 겹쳐 열리고, 열린 패널의 `제목 행 보기`로 A 형에 돌아간다.
- **A 형(패널 접힘):** 계층마다 제목 행을 하나씩 두고(`td[data-tree-depth]`), 스크롤하면 첫 보이는 행을 포함하는 Management Group › Subscription › Resource Group 제목이 머리글 아래에 깊이 순서대로 고정된다. 고정 영역은 표 높이의 50%를 넘지 않고, 고정된 제목을 접으면 그 제목을 제 자리로 먼저 가져온다. 접으면 트리 범위는 해제된다.

배치와 트리 너비는 브라우저 `localStorage`(`armbackup.status-layout`, `armbackup.status-tree-width`)에만 두는 화면 기본 설정이며 서버·Blob에 저장하지 않는다. 주 대상 아래의 종속 행과 `→`/`←`·`Enter` 행 키는 두 배치에서 같다.

### DB 없는 초기 로딩과 일관성

`StateView`는 동일 archive에 화면 DTO의 SHA-256 객체와 완료 marker를 append-only로 저장한다. 업로드→객체/marker readback 검증→scope/config별 최신 포인터 순서로 공개한다. 덮어쓰기는 `console/views/heads/{key}.json`과 수집 상태 `console/views/status/{key}.json`만 허용하며 Blob ETag의 `If-Match`로 교체한다. 원본 백업·뷰 객체·완료 표식은 계속 불변이다. 호스팅 입장은 수집 상태 1회와 포인터→marker→객체 3회의 직접 읽기만 사용하며 백업 원본/입력/호환 marker 목록을 열거하지 않는다. 큰 객체의 SDK 분할 다운로드·재시도는 별도 HTTP 요청이 될 수 있다.

**5분은 수집 주기이지 저장본 폐기 시각이 아니다.** 호스팅에서는 웹 프로세스의 독립 수집 스레드가 방문자 없이 ARM·Activity Log·백업 기록을 수집한다(백업·복원 작업 종료 시 즉시 재수집). HTTP 요청 처리는 저장본 조회 시 ARM 수집을 실행하지 않는다. 수집 시작 시각을 기준으로 `몇 분 전 수집`을 표시하며 15분 초과 또는 마지막 수집 실패는 읽기 전용으로 전환한다. 오래된 정상 저장본은 삭제하지 않는다. 구성·범위·무결성 오류는 명시적으로 표시하며 읽기 경로는 파일을 삭제/재수집하지 않는다. 수집 중 입력 목록이 바뀌거나 포인터 게시가 경합하면 기존 재시도·lease/ETag 보호를 적용한다. 정책/백업 변경은 작업 종료 후 재수집에서 반영되며 시점 원자성을 보장하지 않는다.

호스팅 `GET /api/state`는 저장본을 반환한다. 없으면 빈 성공 화면 대신 HTTP 202/`statePending`과 수집 상태를 알린다. UI는 즉시 미수집/수집 중/실패 화면을 표시하고 1분마다 저장 결과만 확인한다. `fresh=1`도 저장본 조회이며 `POST /api/state/refresh`는 수집을 시작할 수 없다. 세션/상태 요청은 15초 제한으로 응답 실패를 표시한다. 브라우저는 Azure 자격 증명을 보유하지 않는다. 로컬 비호스팅 콘솔만 기존 공용 갱신 POST/poll API와 프로세스 수집을 유지한다. 실제 백업·복원 명령의 서버 검증과 안전 백업은 그대로 유지한다.

현황 미니 달력의 변경 이력과 현재 관계 그래프도 수집기가 저장본에 포함한다. 호스팅 이력/관계 API와 인수인계 보고서는 저장본을 사용하므로 조회만으로 ARM을 호출하지 않는다. 과거 백업 상세·묶음은 Blob 원본의 무결성을 직접 확인한다. 운영자가 명시적으로 요청하는 진단·로그·복원 계획/실행은 기존 실시간 서버 조회를 유지한다.

실환경 화면은 독립 bootstrap 모듈에서 앱과 그 의존 모듈의 로딩 실패를 처리한다. 실패하면 준비 문구만 남기지 않고 오류를 표시하며, 실패한 모듈 의존성을 다시 요청하도록 페이지를 한 번 자동 새로고침한다. 같은 탭에서 연속 실패하면 자동 새로고침을 중단하고 수동 재시도 버튼을 제공한다. `sessionStorage`에 재시도 한도를 기록할 수 없어도 반복 새로고침하지 않는다. 정상 모듈 로딩 후에는 한도를 초기화하며 API 인증 실패나 실행 중 작업을 이 경로에서 자동 재제출하지 않는다.

조회 DTO의 `contentSha256`은 전체 무결성 SHA와 별도로 계산한다. 수집 시작/완료 시각·현재값 조회 시각·수집 실행 상태는 제외하며 실제 형상·존재/권한 상태·최근 변경자/변경 시각·백업·정책·작업 기록·경고는 포함한다. 브라우저는 1분마다 저장 결과를 확인하고 **내용이 달라진 경우에만** 전체 화면을 교체한다. 관측/수집 시각과 오류는 별도로 갱신한다. 검색·선택·접기·그룹 보기·미저장 정책과 스크롤/초점을 보존하며 입력 중이거나 모달을 열었다면 화면 교체를 종료 후로 미룬다. 정상 갱신이 다른 작업의 오류를 지우지 않는다.

150개 자원을 포함한 PC 실환경/명시적 디스크 원천 측정은 기존 입장 API **44.748초**, 새 저장본 API **0.028~0.050초**였다. 브라우저 데이터 표시 확인은 **1.693~2.130초**, 동시 8회 저장본 조회는 **0.064~0.180초**였고 같은 갱신 ID를 사용했다. 새 캐시 형식의 첫 수집은 **33.389초**이며 최초부터 저장본이 없는 경우 이 수집은 필요하다. **App Service/사설 Blob 실측은 아니다.** Blob SDK 계약 테스트에서 직접 읽기 3회·목록 열거 0회·조건부 포인터 교체를 검증했다.

예약 수집도 부모 App Service의 컴퓨트를 사용하므로 Always On·WebJob 실패/미실행 감시가 필요하다. Storage 접근 자체가 실패하면 상태 기록도 남길 수 없으므로 WebJob 이력과 데이터 경과 시각을 함께 확인한다. 수집 입력 목록은 prefix당 10,000개 한도이며 초과는 실패다. 캐시 객체·marker의 장기 retention/인덱스 압축은 운영 확대 전 별도다. 위 PC 측정은 이전 프로세스 수집 방식의 기록이며 WebJob/호스팅 성능 검증은 아니다.

중간 캐시의 JSON/DTO 불완전·SHA 불일치·파일 누락을 발견하면 **해당 포인터·실패한 완료 표식·손상 객체만** ETag/파일 잠금 아래 조건부 삭제하고 다시 수집한다. 정상 다른 scope의 marker/객체와 동시 교체된 정상 포인터는 보존한다. 게시 전 readback이 실패한 객체도 정리하고 최대 3회 안에서 재생성하며 계속 실패하면 명시적 오류를 반환한다. `runs/`, 정책, 작업 기록, 로그와 원본 백업은 삭제 대상이 아니다. **Storage 401/403·통신 오류는 손상으로 취급하지 않고 삭제하지 않는다.** 최초 API는 복구 중임을 HTTP 202/`cacheRecovery`로 알린다.

| 원복·복제 중 일부 실패 | 작업·적용 수·안전 run 보존, 명시적인 재검토. 한 버튼으로 전체 재실행하지 않음 |
| 느린 초기 연결·ARM 일시 오류 | 검증된 저장 뷰 먼저 표시→live 갱신. 캐시 사용을 조회 실패라고 표현하던 혼동을 수정하고 쓰기 잠금 이유를 분리 |

평가 후 위험도 요약/필터를 백업 상태로 교체하고, 날짜별 변경을 행 안의 한 열로 합쳤다. 종류별 그룹에서 클릭한 Resource ID·필터·선택을 유지하고 색 외에 상태 텍스트를 제공한다. 기존 단일 복원과 관계 작업대는 새 이름 NSG/RT 복제와 복합 참조 검토라는 서로 다른 경계를 유지하므로 삭제하지 않았다.

현재 형상의 API 계약 검증 경고는 `current[resourceId].warnings`에 담아 해당 리소스 행의 **현재 형상** 열에 표시한다. 이 경고만으로 백업 수집 실패로 판정하지 않으며, 비교 불가 상태와 복원 제한은 유지한다. 백업이 없는 현재 자원도 최신 보기에서 같은 방식으로 표시한다. 화면 상단 `warnings` 영역에는 관리 그룹·Activity Log 조회와 백업 무결성 등 전체 범위·실행 단위 경고만 표시한다. 경고 접두사의 `kubernetes` 같은 값은 리소스 이름이지 리소스 종류가 아니다.

MSP 엔지니어의 업무를 네 흐름으로 **모델링**했다. 실제 고객 인터뷰나 인력별 사용성 연구 결과로 해석하지 않는다. 실험의 `customer-alpha`/`customer-beta`는 같은 RG 안의 가상 고객 태그이지 실제 고객 테넌트가 아니다.

### 복원 메뉴의 날짜별 백업 탐색

별도 `변경 달력` 메뉴를 제거하고 기존 월~일 **7행**, 주 단위 열의 53주/26주/13주 인터페이스를 **복원 첫 화면**으로 옮겼다. 날짜→해당 날짜의 실제 백업 자원 목록→‘복원 검토’ 순서다. 현황에서 선택한 자원이나 미니 변경 셀에서 진입하면 해당 자원/날짜를 미리 필터링한다. 기존 `#history` 주소는 `#restore`로 연결한다.

색은 **백업 자원 건수**다. 같은 자원의 같은 날 여러 run을 각각 표시하며 변경 없는 백업/첫 백업/안전 백업도 탐색한다. 안전 run은 명시적으로 구분하며 일반 변경 이력 비교의 원천으로 섞지 않는다. 불완전 run·완료 표식 미확인·현재 조회 오류·지원하지 않는 형상은 이유와 함께 선택 불가로 표시한다. 시각 미확인 run은 경고하고 날짜를 만들어 넣지 않는다.

고객·종류·검색·표시 시간대를 달력 집계와 일별 목록에 함께 적용한다. 좌우 방향키는 이전/다음 주, 상하 방향키는 날짜 이동이며 Enter/Space로 날짜를 선택한다. 일반 검증된 백업의 ‘원본 비교’는 불러온 이전/선택 run을 비교하며 현재값을 과거 형상으로 대체하지 않는다. 안전 백업의 상세 비교는 별도로 제공하지 않지만 검증된 경우 복원 원천으로 선택할 수 있다.

선택한 `runId + resourceId`를 다음 절차에 정확히 전달한다. NSG/RT는 기존 방식/근거→서버 계획, Application Gateway/LB 등은 **같은 복원 메뉴 안의** 단일/묶음 계획 작업대로 이어진다. 백업 탐색으로 돌아가는 버튼을 제공하고 적용 전 실시간 재확인·티켓/일회 승인·전체 안전 백업·사후 검증은 유지한다. 여러 RG로의 임의 매핑이나 새로운 복원 프로필을 추가한 변경은 아니다.

초기 화면은 저장된 state DTO의 **불러온 최근 30개 run**을 사용하며 별도 전체 ARM 조회를 기다리지 않는다. 한도 초과 시 더 오래된 백업은 탐색에 포함되지 않는다고 표시한다. 기존 변경 이력 API의 500개 run 제한과 복원 달력의 30개 한도를 혼동하지 않는다.

- [실제 LAB 백업의 일별 탐색·원본 Diff](images/change-calendar-live.png)

색의 진하기는 **변경 자원 수** 또는 **속성 변경 발생 수**다. 위험도와 결합하지 않는다. 같은 자원이 같은 날 여러 번 바뀌면 자원 수는 1개, 발생 기록/속성 변화는 각 비교에서 센다. 빈 날짜는 미관측, 첫 기록은 비교 불가, 검증된 비교의 0건은 변화 없음, 불완전/비호환은 별도 미확인으로 표시한다.

원천은 완료 표식·hash를 확인한 **일반 백업 간 관측**이다. 안전 백업은 기준에서 제외하며, 이후 백업 수집일을 셀 날짜로 사용한다. 실제 변경 시각이나 그 사이 변경·원복 횟수를 확정하지 않는다. 목록 추가/제외는 실제 생성/삭제와 다르게 표시하고, 대상 정책 변화에서 빠진 자원을 삭제로 추정하지 않는다. 첫 형상 기록을 생성 사건으로 세지 않는다.

고객·종류·검색 필터는 달력 집계와 일별 목록에 함께 적용한다. 고객 태그가 바뀐 사건은 양쪽 고객에 보인다. 상세 원본은 기록을 선택할 때 다시 읽어 무결성을 확인한다. 네트워크 지연·수집 오류는 빈 성공 결과로 대체하지 않으며 다른 화면으로 이동한 뒤 오래된 상세 응답을 붙이지 않는다.

실환경 달력은 현재 최근 **500개 run / 10,000개 저장 객체** 읽기 한도를 표시한다. 대규모 장기 운영의 인덱싱/서버 페이지네이션은 후속 최적화 범위다. 현재 실제 이력은 2026-10-31 하루에 집중되어 있어 과거 달력의 빈 칸을 임의 데이터로 채우지 않았다. 예시 모드에서만 명시적인 요일 패턴을 보여준다.

### 실환경 실행·원천

```powershell
.\.venv\Scripts\python.exe -m armbackup.webui --live-config .armbackup-lab\console.local.json --port 8081
```

위 명령의 접속 주소는 **http://127.0.0.1:8081** 이다. `--port`로 다른 loopback 포트를 정할 수 있다. 서버는 하나의 구독·소유 RG 안의 실험 표식과 검토한 프로필만 허용한다. Management Group 계층을 실제 조회한 것처럼 만들지 않는다.

원천은 화면에 계속 표시한다. 기본 `blob` 모드는 사설 Blob을 사용한다. 현재 PC 실험은 구독 정책의 공용 Storage 차단을 존중해 `archive_mode: "local"`과 경로를 **명시적으로 설정**했다. 실제 ARM·Activity Log·Workspace 로그와 로컬 디스크 백업을 구분하며 자동 fallback하지 않는다. 실제 사설 Blob·관리 ID 경로는 일시 Azure 러너에서 따로 검증한다.

### 실환경의 승인·실행

1. 서버가 완료 표식·manifest hash·개별 snapshot hash·Resource ID·지원 API를 확인한다.
2. Create-only/Update-only·티켓·사유를 입력하면 현재 상태를 다시 읽고 서버 계획을 보관한다. 기존 NSG/RT 경로는 **10분**, 복합 단일/묶음 경로는 **60분** 유효하다.
3. 사용자가 대상 이름과 실행 영향을 확인한다. 브라우저는 임의 ARM body 대신 계획 ID·승인 hash·대상 확인만 보낸다.
4. 실행기는 소유/존재 조건·현재 fingerprint·계획 hash를 재확인하고 **일회 실행 표식**을 남긴다.
5. 현재 형상/부재 기록을 별도 저장하고 원본 readback·hash·완료 표식·로그 전송을 검증한다. 실패하면 쓰지 않는다.
6. 적용 직전에 다시 확인하고, 적용 후 전체 검토 프로파일을 비교한다. 불필요한 NoChange 업데이트는 실행하지 않는다.
7. 감사 기록이 영속 저장된 뒤 완료를 반환한다. 실패는 자동 롤백을 의미하지 않으며 안전 백업·현재 상태를 확인한다.

Blob lease와 로컬 file lock은 **같은 저장소의 이 도구들**만 조정한다. Portal·외부 배포 도구·다른 저장소를 사용하는 실행자의 경합을 원자적으로 막지는 못한다. 따라서 운영 자동 복구로 확대하지 않고 격리 LAB에서만 실행한다.

KST/UTC 전환은 표시만 바꾸며 관측값을 다시 읽었다는 뜻이 아니다. 필터·계층 접힘을 유지하고 모바일 메뉴를 닫으면 off-screen 링크의 키보드 포커스를 막는다. 실환경에서는 예시 데이터 모듈도 로드하지 않는다.

기본 현황은 **리소스별 최신 검증된 일반 백업**이다. 이후 run에서 빠진 삭제/제외 자원도 마지막 검증된 소스를 유지하므로 다음 예약/수동 백업이 삭제 행을 숨기지 않는다. 안전 백업은 비교 기준에서 제외하고 복원 이력에서만 선택할 수 있다. 각 행의 실제 source run ID·수집 시각을 사용하며 이 뷰 자체를 새로운 백업이나 원자적 시점으로 표현하지 않는다. 날짜별 단일 run 비교도 그대로 제공한다. 최근 30개 로딩 한계를 넘어선 전체 이력을 모두 관측했다고 주장하지 않는다.

조회·보고서 생성 중에는 이전 관측값과 진행 상태를 명시하고 중복 실행/화면 전환을 제한한다. 최종 관측 시각이 바뀐 뒤에 새 결과로 교체한다. 티켓 query 실패·아직 query하지 않음·빈 실제 query는 서로 다른 상태이며 다른 원천으로 성공처럼 대체하지 않는다.

## 0. 프리뷰 실행과 네 화면


## 1. 요구와 화면의 실체

사용자의 원문:

> 그리고 웹 인터페이스가 있으면 좋겠고, 백업된 형상 목록과 그에 대응하는 현재 형상 목록을 비교하는 리소스 체계를 계층적으로(expand, collapse) 테이블 기반의 뷰가 있었으면 좋겠다.

08:42 KST의 추가 결정:

> TreeGrid의 Row는 개별 리소스를 의미한다면 백업 형상과 현재 형상의 Diff (동일하면 Green, 다르면 Red로)
> 복원UI는 App Service를 사용하도록 하자 (동일 App SErvice Plan 이용)

10:24 KST 추가 요구는 네 화면, Management Group을 포함한 대상 체계·종류·태그, Red/Orange/Yellow 차이 음영, 가능할 때 Activity Log의 변경 주체, 날짜별 백업 선택, 신규 생성/기존 업데이트 구분, 최종 실행 전 현재 시점 안전 백업, 지정 Workspace의 로그 열람이다. 프리뷰는 이 사용자 흐름을 구현하며 실제 Azure 작업은 실행하지 않는다.

제안하는 화면은 **트리 구조의 행과 비교 열을 결합한 TreeGrid**다. 별도 트리에서 자원을 찾고 다른 화면에서 두 JSON을 대조하는 왕복을 줄이려는 목적이다. ≈ 파일 탐색기의 폴더 펼치기와 스프레드시트의 비교 열을 한 화면에 결합한 것이다. 특정 Azure/AWS 제품을 그대로 쓰는 기능이 아니라 armbackup이 구현할 자체 UI다.

W3C의 TreeGrid 패턴도 계층형 표의 자식 행을 펼치거나 접는 구조와 키보드 탐색을 정의한다. 모양만 트리처럼 만들고 키보드·접근성 동작을 빠뜨리지 않는 기준으로 삼는다. (근거: [W3C TreeGrid 패턴][treegrid])

## 2. 화면 구성안

상단에는 다음을 둔다.

- **백업 선택:** UTC/KST 시각·run ID·Captured/Incomplete·커버리지. 실패/불완전 백업은 경고하고 완전한 백업처럼 취급하지 않는다.
- **대상 범위:** 구독·RG·유형 필터, 이름/Resource ID 검색, 변경·미확인만 보기.
- **현재 조회 상태:** 비교 시작/종료·마지막 조회 시각·진행·부분 실패·새로고침.
- **요약:** 동일·변경·백업에만·현재에만·대기/미확인 건수. 그룹 행과 같은 자원을 중복 합산하지 않는다.

본문은 계층형 비교 테이블, 행 선택 후 상세 패널은 속성 비교로 구성한다. 아래는 **운영 데이터 모델의 가상 레이아웃 예시이며 실제 KT 상태가 아니다.** 현재 프리뷰의 실제 화면은 위 캡처를 참고한다.

| 리소스 계층 | 유형 | 백업 시점 | 현재 조회 | Diff |
| --- | --- | --- | --- | --- |
| ▼ 구독 A | 구독 자원 | 있음 | 있음 | Green / 자체 설정 동일 |
| 　▼ rg-app | RG 자원 | 있음 | 있음 | Green / 자체 설정 동일 |
| 　　▼ nsg-web | NSG | 있음 | 있음 | Red / 변경 |
| 　　　AllowHTTPS | 실제 ARM 하위 규칙 자원 | 포트 443 | 포트 8443 | Red / 변경 |
| 　　nsg-old | NSG | 있음 | 없음 확인 | Red / 백업에만 |
| 　　nsg-new | NSG | 없음 | 있음 확인 | Red / 현재에만 |

**리소스 행 1개는 Resource ID로 식별되는 개별 자원 1개**다. 속성은 그 행의 상세 Diff 패널에서 비교하며, 일반 JSON 속성을 펼쳐 개별 자원인 것처럼 표시하지 않는다. 실제 하위 자원일 때만 자원 행으로 연결한다.

최신 요구는 Green과 Red/Orange/Yellow 음영이다. 프리뷰는 Red=위험 변경/현재 부재, Orange=그 외 구성 변경, Yellow=태그·설명만 변경, Green=비교 범위 내 동일, Gray=미확인을 제안한다. 보안 관련 명시적 예시 속성이나 NSG 규칙 차이는 Red로 분류하지만 **Azure가 산출한 위험 등급이나 모든 유형의 운영 영향 평가가 아니다.** 여러 차이가 있으면 가장 높은 제안 등급을 사용한다.

음영과 함께 텍스트·아이콘 배지를 제공해 색만으로 상태를 전달하지 않는다. (근거: [WCAG 색상 사용 기준][use-color])

### 계층과 상호작용

최신 표시 계층은 `Management Group → Subscription → Resource Group → 백업 리소스`이며 실제 ARM 하위 자원을 백업했다면 그 아래에 연결한다. 프리뷰의 MG·Subscription·RG는 **리소스 행과 구별되는 중립 집계 헤더**이며 복원 선택·Diff 집계에 섞지 않는다. 운영에서 구독/RG 자체의 백업을 비교하는 경우 해당 실제 Resource ID와 자체 Diff를 집계 헤더와 분리해 표현해야 한다.

부모 자원 자체의 Diff와 “하위 자원 변경 N건” 집계는 구분한다. 자식이 Red라는 이유만으로 부모 자체를 자동 Red로 만들지 않는다. 다만 부모의 비교 payload에 포함된 하위 설정이 실제로 달라졌다면 부모의 비교 규칙에 따라 Red가 될 수 있다.

- 행별 펼치기/접기, 선택 범위 펼치기/접기, 필터 적용 후 조상 경로 유지.
- 이름/상태 정렬은 같은 부모의 형제 행 안에서 적용해 트리를 깨지 않음.
- 자원 선택은 상세 패널을 열고, expand/collapse와 선택 동작은 구분.
- 키보드 탐색·포커스 표시·`aria-expanded` 등 접근성 의미 제공. ([TreeGrid 기준][treegrid])
- 조회 중·비어 있음·부분 실패·재시도 상태를 별도 표시. 오류 시 빈 표만 보여주지 않음.

실제 하위 자원은 Resource ID의 구조·유형별 collector를 통해 구성한다. 임의 문자열 prefix나 표시 이름만으로 부모를 찾지 않는다. VNet의 subnet 같은 하위 구조와 NIC→NSG 같은 **참조/의존 관계는 구분**하며 후자는 별도 관계/상세 영역에 표시한다. 부모 원본에 포함된 하위 값과 독립된 하위 자원 행을 중복 작업·중복 집계하지 않도록 한다. (계층 모델 설계 제안)

## 3. 비교 데이터 계약

### 양측 목록과 대응

| 데이터 | 제안하는 원천 |
| --- | --- |
| 백업 목록 | Blob의 run/manifest/완료 상태 |
| 백업 형상 | 선택한 run의 원본·보완 수집·API 버전·hash |
| 현재 목록 | 같은 비교 스코프의 ARG Discovery |
| 현재 상세 | 해당 RP REST 조회와 필요한 보완 collector |
| 실행/오류 추적 | 지정 Log Analytics Workspace |

Log Analytics를 형상 원본 저장소로 바꾸지 않는다. 백업 원본은 Blob에 두고, 브라우저가 관리 ID나 토큰을 받아 ARM/Blob을 직접 호출하지 않도록 Python 서버 측 조회 API를 설계한다. (설계 제안)

같은 환경의 기본 매칭 키는 정규화한 **전체 ARM Resource ID**다. 원래 표기를 보존하고 현재 코드의 대소문자 처리와 정합성을 맞춘다. 자원 이름만으로 다른 구독/RG의 자원을 매칭하지 않는다. 다른 환경 복제 비교는 별도의 target 매핑이 있어야 하며 기본 비교와 섞지 않는다.

백업과 현재 양측 ID의 합집합을 먼저 구성해야 한다. 백업 목록만 순회하면 백업 이후 추가된 자원을 놓치고, 현재 목록만 순회하면 없어진 자원을 놓친다. 다만 목록의 미관측과 실제 부재는 같은 뜻이 아니다.

### 상태 정의안

| 상태 | 표시 | 판정 조건 |
| --- | --- | --- |
| **동일** | **Green** + 동일 | 양측 상세를 읽고 호환되는 규칙으로 비교한 범위가 같음. “비교 범위 내 동일”로 해석 |
| **위험 변경** | **Red** + 위험 변경 | NSG 규칙·명시적 보안 속성 등의 차이. 유형별 운영 정책 검증 전의 제안 분류 |
| **구성 변경** | **Orange** + 구성 변경 | 태그 외 형상 차이 중 프리뷰의 Red 조건이 아닌 경우 |
| **경미 변경** | **Yellow** + 경미 변경 | 차이가 태그·설명에만 있는 경우. 실제 영향이 낮음을 보장하지 않음 |
| **백업에만** | **Red** + 백업에만 | 백업에는 있으며 현재 부재를 신뢰할 수 있게 확인함 |
| **현재에만** | 별도 중립 안내·목록 | 현재 존재를 확인했지만 선택 백업에 없음. 최종 백업 행이나 자동 삭제 대상으로 포함하지 않음 |
| **비교 대기** | Gray 등 중립 + 대기 | 목록은 확보했지만 상세 조회·비교를 아직 하지 않음 |
| **미확인** | Gray/Amber 등 중립·주의 + 사유 | 권한/통신/수집 오류·불완전 범위·API/정규화 비호환 때문에 판정할 수 없음 |

**Diff 색상과 조회/복원 작업 성공·실패는 다른 축**이다. 조회 실패를 Red 형상 차이로 표시하거나, 작업이 끝났다는 이유로 Green 동일을 표시하지 않는다. 한쪽 자원의 부재는 차이를 확인한 경우만 Red로 두고 불완전 범위나 오류라면 미확인이다.

ARG는 비동기 색인이므로 ARG에서 보이지 않는다는 이유만으로 “삭제됨”을 확정하지 않는다. 중요한 상태 판단에는 RP 조회를 결합한다. 401/403·timeout·하위 API 실패는 미확인이다. RP의 404도 대상 ID·부모 범위·권한과 오류 의미를 확인하고 판정한다. (근거: [ARG와 RP 혼합 조회 지침][arg-strategy]; UI 상태 분류는 설계 제안)

백업이 Incomplete이거나 해당 유형/범위가 제외됐었다면, 현재 자원이 백업에 없다는 이유로 “백업 이후 생성됨”을 확정하지 않는다. 비교 범위 밖/당시 미수집 사유를 표시한다.

### 시각·정규화·속성 차이

“현재 형상”은 실제 읽은 시점의 관측값이다. ARG 목록 시각과 각 RP 상세 조회 시각을 구분하고 캐시를 쓰면 시각·새로고침 상태를 표시한다. 백업도 다중 자원의 원자적 시점 스냅샷이 아니므로 한 시각의 전체 일관성을 주장하지 않는다.

상세 패널의 기본 표는 다음 열을 가진다.

| 속성 경로 | 백업 값 | 현재 값 | 판정 |
| --- | --- | --- | --- |
| `properties.securityRules[AllowHTTPS].destinationPortRange` | 443 | 8443 | 변경 |

- 이름·형상과 별개인 provisioning 상태·읽기 전용 값·타임스탬프 등은 유형별 비교 규칙에 따라 분리한다. 모든 유형에 공통 삭제 규칙을 무작정 적용하지 않는다.
- JSON 객체의 키 순서 차이는 정규화하되 **배열은 의미를 확인**한다. 이름이 키인 규칙 배열과 순서 자체가 의미인 배열을 똑같이 정렬하지 않는다.
- `null`·필드 부재·미수집·기본값을 무조건 같은 값으로 합치지 않는다.
- API 버전 차이로 필드가 다르면 변환/비교 가능한 속성 범위를 명시한다. 지원하지 못하면 미확인/비교 불가로 남긴다.
- 비밀값은 기본적으로 원문 노출·전송을 피하고 비교 제외 사유를 표시한다. 양쪽이 같은 마스킹 문자열이라는 이유로 실제 값이 같다고 판정하지 않는다.

정규화 정책 버전·비교 대상 API·비교 완료 시각도 결과에 연결한다. 원본 JSON 확인은 권한과 마스킹 정책을 별도로 검토한 뒤 제공한다. (비교 엔진 설계 제안)

## 4. 복원 설계와 연결하되 실행은 분리

| 비교 결과 | 가능한 다음 검토 |
| --- | --- |
| 백업에만 | 대상 부재·유형 지원·의존성을 확인한 뒤 Create-only 계획 후보 |
| 변경 | 복원할 속성과 정상 변경 보존 정책을 정한 뒤 Update-only 계획 후보 |
| 동일 | 쓰기 없이 확인·감사 기록 |
| 현재에만 | 백업 대비 신규/범위 차이 검토. **자동 삭제·덮어쓰기 대상 아님** |
| 대기/미확인 | 상세 재조회·범위/오류 해결. 자동 복원 판단 금지 |

이는 [Create-only/Update-only 검토안](restore.md)과의 연결 제안이다. 비교 결과나 행 선택이 실행 승인이 되는 것은 아니다. 실제 적용 직전에 RP 상태·계획 전제를 다시 확인해야 한다.

**프리뷰는 단일 리소스 복원 마법사를 제공하지만 운영 실행기는 연결하지 않는다.** 현행 `--allow-existing`을 그대로 웹 버튼에 연결하지 않는다.

1. 선택한 리소스의 날짜별 백업 이력에서 완료된 형상을 고른다.
2. **신규 생성:** 대상 Subscription·RG·이름을 입력한다. 대상이 있거나 미확인이면 차단한다. **업데이트:** 선택 원본이 현재 존재해야 하며, 없어져도 신규 생성으로 바꾸지 않는다.
3. 현재 재확인 → 안전 백업 → 적용 → 사후 비교 절차와 한계를 설명하고 최종 확인을 받는다.
4. 현재 예시 상태의 안전 백업을 먼저 별도 저장한다. 신규 대상이 없으면 부재 기록을, 원본 현재 형상이 있으면 함께 보관한다. 원본도 없으면 부재 기록만 남기며 이를 존재하는 형상으로 꾸미지 않는다.
5. 저장 성공 뒤 예시 형상을 적용·저장하고 비교한다. 안전 백업 실패 시 적용하지 않으며, 적용 저장 실패 시 안전 백업과 기존 현재값을 보존한다. 검토/안전 백업 이후 예시 revision이 바뀌면 재검토한다.

이 순서는 `localStorage` 기반 프리뷰의 동작이다. 운영에서는 저장소 완료 표식·무결성·수집 완전성·실행 직전 상태·RP 조건부 쓰기·인가·계획 승인·감사 로그를 서버 측에서 검증해야 한다. 프리뷰의 revision 검사는 Azure Portal이나 다른 도구의 변경을 잠그지 않는다.

### 변경 주체와 Log Analytics 연결 설계

Activity Log의 Administrative 이벤트에는 ARM 관리 작업과 `caller`가 기록될 수 있다. 운영 연동 시 Resource ID·성공한 변경 작업·관측 기간을 기준으로 최신 관련 이벤트와 시각을 보여주는 방향이다. 호출 주체가 애플리케이션일 수 있고, 관련 로그가 없거나 권한/조회에 실패하면 **미확인**으로 표시한다. 형상 비교 결과만으로 사람이나 “이 Diff의 원인”을 확정하지 않는다. 기본 Activity Log 보관은 90일이며 장기 이력에는 별도 내보내기·보존 정책이 필요하다. ([이벤트 스키마][activity-schema], [보관·조회][activity-log])

로그 화면의 운영 원천은 지정한 Log Analytics Workspace다. 기존 `events.py`의 DCR 필드는 `TimeGenerated`, `RunId`, `Level`, `Event`, `ResourceId`, `Status`, `ErrorCode`, `Details`다. 프리뷰의 읽기 쉬운 메시지·상관관계 ID는 **화면용 예시 모델**이며 기존 테이블에 `Message`나 `CorrelationId` 열이 있다고 가정하지 않는다. 서버 어댑터에서 실제 `Event`/`Details`를 표시 모델로 변환해야 한다.

Logs Query API는 Workspace **GUID**와 KQL·기간을 받는다. 기존 설정의 Workspace **ARM Resource ID**, Logs Ingestion endpoint·DCR을 조회 endpoint/Workspace GUID와 혼동하지 않는다. 서버 측 자격증명·읽기 권한·Workspace 범위 인가·사설 조회 경로·부분 실패 처리가 별도로 필요하다. 브라우저에 토큰을 주거나 임의 KQL/Workspace를 실행하는 proxy를 만들지 않는다. 현재 프리뷰는 이 API를 호출하지 않는다. ([공식 요청 형식][logs-query])

## 5. App Service 호스팅·규모·접근 통제

### 확정 호스팅과 권장 앱 분리

**사용자 확정:** 복원/비교 UI는 App Service에 호스팅하고 백업 WebJob 실행기와 동일 App Service Plan을 이용한다. UI를 추가한다는 이유로 별도 Plan을 기본 생성하지 않는다.

**권장 구성:** 같은 Plan 안에서 백업 전용 Web App과 비교/복원 UI용 Web App을 나누고 각각 별도 관리 ID를 부여한다. Plan은 공유하면서 앱 설정·배포·신원/RBAC의 책임을 나누기 위한 제안이며, 별도 Web App 수까지 사용자가 확정한 것은 아니다. 백업 신원에 복원 write 권한을 합치지 않는다. 실제 복원 executor와 승인 경로는 아직 미정이다.

같은 Plan의 앱/WebJob은 **CPU·메모리·기본 컴퓨트와 스케일을 공유**한다. 별도 앱이 곧 컴퓨트/장애 영향 격리나 비용 0원을 뜻하지 않으며, 수집 부하와 UI 응답성·기존 Plan 여유를 함께 검증한다. 관리 ID는 앱별로 구성할 수 있지만 동일한 광범위 신원을 다시 공유하면 권한 분리가 되지 않는다. (근거: [App Service Plan][hosting-plan], [앱 관리 ID][app-identity])

UI 앱에도 VNet Integration·Blob/DCE 사설 DNS·필요한 아웃바운드 경로를 구성하고 확인한다. 같은 Plan을 쓴다는 사실만으로 백업 앱의 네트워크·권한 설정이 UI에 자동 적용된다고 가정하지 않는다. 사용자 인바운드 PE·인증/인가·SCM 경로도 준비한다. 구체적인 연결·배포는 [배포 문서](deployment.md)를 따른다. (구성 권고)

### 규모·접근 통제

대규모 자원을 한 번에 모두 브라우저 DOM에 넣거나 모든 행에서 RP GET을 반복하지 않는다. 하위 목록 지연 로딩·페이지네이션/가상화·제한된 배치 조회·캐시/새로고침·취소를 검토한다. “모두 펼치기”도 선택한 범위와 로드 한도를 명확히 한다. 상세 비교 전의 행은 동일이 아니라 대기다.

필터·백업 선택을 바꾸면 이전 비동기 결과가 새 비교 화면에 섞이지 않도록 comparison ID로 구분한다. 정렬·필터 변경 후 펼침/포커스 상태 보존도 시험한다. 그룹 요약은 로드된 일부 결과인지 전체 결과인지 표시한다.

보안/운영은 다음을 추가 설계한다.

- 사설 접속 경로 외에 **사용자 인증·역할·조회 가능한 구독 범위**를 통제한다. PE만으로 사용자를 인가했다고 보지 않는다.
- UI 사용자가 서버 관리 ID의 전체 권한을 무조건 사용할 수 없도록 서버 측 범위 검사를 한다. 임의 ARM URL/Blob 경로를 요청받는 범용 proxy로 만들지 않는다.
- 브라우저에는 필요 최소값만 전달하고 토큰·설정 파일·비밀값·전체 원본의 무분별한 로깅을 피한다.
- 비교 조회·오류·미확인·새로고침의 추적 ID를 Log Analytics와 연결한다.
- 백업 신원과 UI/복원 관련 신원을 분리한다. 같은 Plan의 자원 공유와 앱별 인증/권한 경계를 혼동하지 않는다.

프레임워크·라이브러리·상세 API 경로·캐시 TTL·최대 행 수·브라우저 성능 기준·사용자 권한 모델은 아직 미선정이다. 새 의존성이나 Azure 리소스는 이번 요구 정의에서 추가하지 않았다.

## 6. 구현 상태·순서와 인수 기준

현재 [webui.py](../src/armbackup/webui.py)는 loopback 프리뷰/실환경과 명시적 `--hosted` 모드를 구분한다. 프리뷰의 `connect-src 'none'`은 유지하고 실환경은 same-origin API를 사용한다. [정적 자산](../src/armbackup/ui_static)은 wheel과 콘솔 배포 ZIP에 포함한다. WebJob의 health host와 콘솔 서버는 별개다.

프리뷰의 비교 모델은 예시 정책 `demo-v1`이다. 객체 키 순서, 검토한 예시의 읽기 전용 값, NSG/Route Table 이름 기반 배열만 정규화한다. 다른 배열 순서·필드 부재·`null`을 합치지 않으며 API 불일치·마스킹·불완전 백업은 미확인으로 둔다. 이 브라우저용 모델을 운영의 모든 RP에 검증된 비교 엔진으로 취급하지 않는다.

**LAB에서 구현한 기능:** 저장소 무결성, 실제 인벤토리/정책, 일별 달력/속성 Diff, Activity Log, Workspace 감사, 단일/묶음 선택·포함/공유 경계·의존 순서·일회 계획·전체 안전 백업·전체 사후 비교, Gateway health/WAF 로그, 작업 기록·보고서.

**아직 없는 운영 기능:** 다중 사용자 역할 분리·교차 테넌트/여러 고객 workspace·실제 MG Discovery·운영 대량 처리·일반 자동 복구. 지정 단일 운영자의 Entra 호스팅은 [배포 문서](deployment.md)를 따른다. [Blob 어댑터](../src/armbackup/archive.py)의 제한된 prefix 열람과 [로컬 검증 어댑터](../src/armbackup/local_archive.py)는 원천·규모를 구분한다.

운영 연동의 권장 구현 순서:

1. 백업 run 목록·명세 확인, 현재 스코프 조회와 비교 ID/시각 계약.
2. 양측 ID 합집합·상태/미확인 모델, 부모/보기 그룹 구성.
3. 서버 측 상세 수집·유형별 정규화와 속성 차이 엔진.
4. 프리뷰의 TreeGrid·상세·설정을 실제 API와 연결하고 키보드·접근성·레이스 처리를 재검증.
5. 인증/인가·대량 자원·부분 실패·캐시/새로고침 검증.
6. 별도 결정된 복원 계획·승인과의 연계.

최소 인수 기준안:

- 양측 존재/차이·백업에만·현재에만·대기·권한/통신 오류를 혼동하지 않는다.
- 확장/축소 후 부모 경로·정렬·필터와 키보드 포커스가 유지된다.
- 개별 자원 행의 자체 Diff가 동일이면 Green, 확인된 차이는 합의한 Red/Orange/Yellow 정책으로 표시하며 대기/미확인은 중립 상태다. 비자원 그룹 헤더를 자원 행으로 세거나 선택하지 않는다.
- 미수집 범위·API 비호환·마스킹된 설정을 “동일”로 확정하지 않는다.
- 백업 선택/새로고침 시 오래된 결과가 새 화면에 섞이지 않는다.
- 대량 목록은 점진적으로 로딩되고 전체/부분 집계가 구분된다.
- 로컬 프리뷰에서 ARM PUT/DELETE·실제 복원이 발생하지 않는다. 운영 연동 전에는 안전 백업 실패·미확인 상태·모드 전제 변경을 서버에서도 차단한다.
- UI와 백업 앱이 같은 App Service Plan을 참조하는지 확인하고 공유 부하·개별 네트워크/신원 구성을 시험한다.

프리뷰의 모델·렌더·주요 키보드 조작·브라우저 시나리오는 [검증 기록](validation.md)에 구분한다. 전체 접근성 적합성 인증·대량 자원 성능·KT 실환경 조회·운영 복원은 검증하지 않았다.
